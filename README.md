# Service Network Optimizer

**정비 서비스망(하이테크센터 · 블루핸즈)의 지역별 수요를 차령 구조로 추정하고, 커버리지 갭과 거점 품질을 진단한 뒤, 같은 예산을 신설과 증설 중 어디에 써야 하는지 최적화로 답한다.**

```bash
pip install -e ".[dev]"
snx pipeline --source sample     # 수집 → 수요 → 커버리지 → 품질 → 입지 · 투자 최적화 → 리포트 → 지도
streamlit run app/dashboard.py   # 대시보드
```

API 키 없이 바로 끝까지 돈다. 공개 참조표 위에서 재현 가능한 합성 데이터를 만드는 `sample` 모드가 기본값이다. 실제 통계 파일을 `data/raw/` 에 넣으면 `--source live` 로 같은 파이프라인이 그대로 돈다.

---

## 왜 이 문제인가

국내 서비스 네트워크는 대개 **과거 판매 실적**을 따라 깔려 있다. 그런데 정비 수요를 만드는 것은 판매량도 인구도 아니라 **지금 도로 위를 달리는 차량의 나이**다. 이 둘이 어긋나면 서비스망에 네 가지 질문이 생긴다.

| 질문 | 답하는 모듈 | 산출 |
|---|---|---|
| 어느 지역 고객이 30분 안에 정비를 못 받는가 | `demand` · `coverage` | 접근성 갭 / 용량 갭 분리, 갭 스코어 |
| 불만이 많은 거점은 붐벼서인가, 운영이 약해서인가 | `quality` | 거점별 품질 등급 · 원인 유형 · 처방 |
| 같은 예산이면 새로 짓는 게 나은가, 늘리는 게 나은가 | `optimize` | 신설 · 증설 동시 최적 투자안 |
| 보증 연장 · 멤버십 정책이 성공하면 서비스망이 감당하는가 | `policy` | 정책 시나리오별 누수율 · 과부하 상권 |

원인을 구분하지 않으면 처방이 틀린다. 불만 많은 지역에 무조건 거점을 짓거나, 운영 문제를 증설로 덮거나, 정책 효과를 네트워크 용량이 삼키는 일이 생긴다. 이 프로젝트는 각 질문에서 **원인을 분리하고, 원인별로 다른 처방**을 낸다.

## 실행 결과 (sample 모드, 시드 고정)

```
연간 정비 입고 수요       4,214,724건   (보증수리 19.1%)
미충족 수요                 640,247건   (15.2%)
30분 접근 공백 시군구             1곳
건전 부하율(85%) 초과 상권       43곳

거점 품질   과부하형 60곳 · 운영형 45곳 · 대기 리스크 130곳   (부하율–VOC 순위상관 0.39)

예산 450억원      흡수 수요     해소율
  신설만           143,550      22.4%    ← 신규 거점 15개소
  증설만           244,030      38.1%
  최적 조합        244,030      38.1%    ← 신설 0 · 증설 71곳(+180베이), 신설만 대비 1.70배

정책 시나리오  6~10년 차 공식망 유입률 38% → 50%
  입고 +407,019건 중 48%(194,687건)가 대기 · 이탈로 샘, 과부하 상권 43 → 53곳
```

숫자보다 결론이 중요하다.

1. **현재 갭은 거의 전부 용량 갭이다.** 30분 공백 지역은 1곳뿐이고, 미충족의 대부분은 거점은 닿지만 붐비는 곳에서 나온다.
2. **그래서 이 예산 규모에서는 증설이 신설을 이긴다.** 증설만으로 해소할 수 있는 상한은 51.9만 건(미충족의 81%)이다. 나머지(30분 밖 수요, 증설 한도를 넘는 집중 과부하)는 신설로만 풀리므로 예산이 커질수록 신설 비중이 올라간다.
3. **불만의 원인은 둘로 갈린다.** 부하와 VOC의 상관(0.39)은 증설이 곧 품질 투자라는 뜻이다. 반면 운영형 45곳은 증설로 고쳐지지 않는다.
4. **유입률을 올리는 정책은 증설 계획과 한 세트여야 한다.** 늘어난 입고의 절반이 거점 용량에 막히면 고객 경험은 오히려 나빠진다.

## 무엇을 만들었나

```
등록 통계 · 인구 · 서비스망 · VOC
        │
        ├─ [1] 수요 추정       차령 버킷별 정비 원단위 × 공식망 유입률
        │                      → 시군구별 연간 입고, 보증수리 / 유상 분해
        │
        ├─ [2] 커버리지 진단    30분 상권 판정 + Huff 수요 분배 + 거점 부하율
        │                      → 접근성 갭 / 용량 갭 분리 → 갭 스코어 (0~100)
        │
        ├─ [3] 거점 품질 진단   추정 대기일수 · VOC · 재입고율
        │                      → 품질 등급 A~D, 과부하형 / 운영형 / 대기 리스크
        │
        ├─ [4] 투자 최적화     (a) 신규 거점 p개소 — 용량제약 최대커버링 (MCLP)
        │                      (b) 신설 + 증설 예산 동시 최적화 (MILP)
        │
        ├─ [5] 정책 시나리오   공식망 유입률 변경 → 수요 · 커버리지 재계산 → 누수율
        │
        └─ [6] 리포트 생성     CrewAI 3-에이전트 순차 파이프라인 (없으면 템플릿)
                              → 임원 보고용 한국어 리포트 + 지도 + 대시보드
```

### 1. 수요는 차령이 만든다 — 그리고 보증이 비용 구조를 가른다

```
D_i = Σ_a  N_ia · r_a · λ_a          W_i = Σ_a  D_ia · ω_a
```

`N_ia` 지역 i · 차령버킷 a 의 자사 보유대수, `r_a` 연간 정비 입고 원단위, `λ_a` 공식 서비스망 유입률, `ω_a` 보증수리(무상) 비중.

차령이 오르면 `r_a` 는 커지지만 `λ_a` 는 더 빠르게 떨어진다. 11년 이상 된 차는 일반 정비소로 빠져나가기 때문이다. 이 비선형성 때문에 **"인구는 적은데 수요는 많은 지역"** 과 **"차는 많은데 공식망 수요는 적은 지역"** 이 갈라진다. 전기차는 배터리 보증이 길어서 `ω` 를 따로 두었다. 젊은 차가 많은 대도시는 보증 비용 부담이, 노후차가 많은 지방은 유상 정비 수요가 크다.

### 2. 수요를 한 거점에 몰아주지 않는다

최근접 거점에 100%를 배정하면 거점이 촘촘한 대도시의 부하가 과대평가된다. 그래서 소요시간에 반비례하는 Huff 가중치로 나눠 배정한다.

```
w_ij ∝ max(t_ij, 5분)^(-1.4)      Σ_j w_ij = 1  (30분 내 거점이 있을 때)
```

거점 부하가 건전 수준(85%)을 넘은 만큼은 대기로 남는다. 30분 안에 거점이 없어서 못 받는 수요는 **접근성 갭**, 거점은 있지만 붐벼서 대기로 남는 수요는 **용량 갭**으로 나눠 센다.

### 3. 같은 불만, 다른 원인

```
대기일수 = base · (1 + ρ / (1 − ρ))        품질 리스크 = 0.40·대기 + 0.35·VOC + 0.25·재입고
```

| 부하 \ 불만 | 불만 신호 있음 (VOC · 재입고 상위 15%) | 없음 |
|---|---|---|
| **건전 부하율 초과** | 과부하형 품질저하 → 워크베이 증설 · 예약 분산 | 대기 리스크 → 예방적 증설 검토 |
| **정상 부하** | 운영형 품질저하 → 정비 품질 점검 · 기술 교육 | 정상 |

부하율이 1에 가까워질수록 대기가 비선형으로 늘어난다. 그래서 부하율 80% 거점과 95% 거점은 체감 품질이 전혀 다르다. 한편 한가한데도 불만이 많은 거점은 증설로 고쳐지지 않는다. 이 둘을 섞으면 운영 문제에 설비 투자를 하게 된다.

### 4. 갭 순위대로 짓지 않는다 — 그리고 짓는 것만이 답이 아니다

**(a) 신규 거점 입지 — 용량제약 최대커버링.** 갭 상위 지역은 서로 붙어 있는 경우가 많아서 1·2·3위에 차례로 지으면 같은 수요를 여러 번 덮게 된다.

```
max  Σ v_ij · z_ij                    v_ij = 1 + α(1 − t_ij/T)
s.t. Σ_j z_ij ≤ unmet_i   Σ_i z_ij ≤ C · x_j   z_ij = 0 if t_ij > T   Σ_j x_j ≤ p
```

**(b) 신설 + 증설 동시 최적화.** 증설은 대기(용량 갭)만 풀 수 있고 단가가 낮다. 신설은 두 갭을 모두 풀지만 비싸다. 두 수단을 한 예산 안에서 경쟁시킨다.

```
변수   x_k ∈ {0,1} 신설    y_j ∈ {0..4} 증설 베이    z_ik 신설 흡수    e_ij ≤ o_ij 증설 흡수
max    Σ v_ik z_ik + Σ v_ij e_ij
s.t.   Σ_k z_ik + Σ_j e_ij ≤ unmet_i       한 수요를 두 번 세지 않는다
       Σ_i z_ik ≤ C · x_k    Σ_i e_ij ≤ h · y_j
       F · Σ x_k + c · Σ y_j ≤ B
```

`o_ij` 는 커버리지 진단의 Huff 배정에서 나온 "지역 i 가 거점 j 에서 겪는 대기량"이다. 진단과 최적화가 같은 배정을 보므로 숫자가 서로 어긋나지 않는다.

### 5. 정책은 네트워크와 따로 돌지 않는다

보증 연장이나 정비 멤버십은 대부분 공식망 유입률 `λ_a` 를 올리는 정책이다. `snx scenario` 는 유입률만 바꾼 설정으로 수요와 커버리지를 메모리에서 다시 계산하고, **늘어난 입고 중 서비스망이 받지 못하는 비율(누수율)** 과 지역별 영향을 보여 준다. DB는 건드리지 않으므로 대시보드 슬라이더로 가볍게 여러 번 돌려 볼 수 있다.

### 6. 에이전트는 숫자를 만들지 않는다

CrewAI 3-에이전트(수요 애널리스트 → 서비스망 전략가 → 보고서 작성자)가 순서대로 리포트를 쓴다. 설계 원칙은 하나다. **에이전트에게는 DB 조회 도구만 준다.** 모든 수치는 `agents/tools.py`(도구 8종)가 SQLite 에서 읽어 JSON 으로 돌려주고, 에이전트는 그 위에 해석과 서술만 얹는다.

`OPENAI_API_KEY` 가 없으면 조용히 결정론적 템플릿 리포트로 대신한다.

## 사용법

```bash
# 단계별 실행
snx init                                  # DB 스키마 생성
snx ingest --source sample                # 차량 모수 · 서비스망 · VOC 수집
snx demand                                # 지역별 정비 수요 (보증 / 유상 분해)
snx analyze                               # 커버리지 · 갭 스코어
snx quality                               # 거점 품질 진단
snx optimize --p 20                       # 신규 거점 20개소 최적 배치
snx plan --budget 900                     # 예산 900억원 신설 + 증설 동시 최적화
snx scenario --loyalty 6-10=0.50          # 정책 시나리오 (반복 지정 가능)
snx report --no-agent                     # 템플릿 리포트
snx map                                   # 지도 HTML

# 전 단계 일괄
snx pipeline --source sample --p 15 --budget 450

# 예산 규모별 민감도
for b in 225 450 900; do snx plan --budget $b; done
```

설정은 전부 `config/settings.yaml` 에 있다. 정비 원단위, 공식망 유입률, 보증수리 비중, 접근 기준 시간, 평균 주행속도, 갭 스코어 가중치, 품질 리스크 가중치, 신설 · 증설 단가, 기본 정책 시나리오를 코드 수정 없이 바꿔 시나리오를 돌릴 수 있다.

### live 모드로 전환

`data/raw/` 에 파일을 놓으면 된다. 형식과 출처는 [docs/data_sources.md](docs/data_sources.md) 에 정리했다.

| 파일 | 내용 | 출처 |

| `service_centers.csv` | 거점 목록(좌표 · 워크베이) | 공식 서비스망 안내 · 사내 네트워크 마스터 |
| `center_voc.csv` (선택) | 거점별 VOC · 재입고율 반기 집계 | VOC 관리 시스템 · 정비 이력 |

## 구조

```
src/snx/
├── config.py            settings.yaml → pydantic 검증 (전역 상수 없음)
├── cli.py               typer CLI — 단계별 / 일괄 실행
├── ingest/              sample 합성 생성기 · live 원본 로더 (동일 인터페이스)
├── storage/             SQLite 어댑터 + schema.sql (단계 산출물 물질화)
├── demand/              차령 기반 수요 추정 · 보증수리 분해 · 수요 구성 분해
├── coverage/            거리 · 소요시간 / 용량 / Huff 배정 · 갭 스코어링
├── quality/             거점 품질 스코어카드 (대기 · VOC · 재입고, 원인 분리)
├── optimize/            siting.py 신규 거점 MCLP · network_plan.py 신설+증설 MILP (PuLP · CBC)
├── policy/              공식망 유입률 정책 시나리오
├── agents/              CrewAI 크루 + 조회 도구 8종 + prompts/*.yaml
├── report/              근거표 조립 · 마크다운 렌더링
└── viz/                 folium 지도
app/dashboard.py         Streamlit 대시보드
tests/                   64 tests
```

단계 산출물은 메모리가 아니라 SQLite 에 저장한다. 그래서 각 단계를 따로 다시 돌릴 수 있고, 대시보드와 에이전트가 같은 데이터를 읽는다.

- **수요**: 폐형해 일치, 보증 분해 합 = 전체, 전기차 배터리 보증
- **커버리지**: 경계조건 (무거점 · 원거리 · 과부하)
- **품질**: 2×2 원인 분리, VOC 없는 환경 폴백, 대기일수 비선형성
- **최적화**: 예산 제약, 흡수량 상한, 거점 수 단조성, 혼합안 ≥ 단일 수단, 단가 변화에 따른 신설 전환
- **정책**: 기준값 불변 시 영향 0, DB 비오염
- **통합**: 전 테이블 적재, 미충족 비율의 현실성

## 한계

- 소요시간은 직선거리 기반 근사치다. 산악 · 도서 지역 접근성이 실제보다 낙관적으로 나온다.
- 정비 원단위 · 공식망 유입률 · 보증수리 비중 · 신설/증설 단가는 시나리오 가정값이다. 실적 데이터로 바꾸면 절대 수준은 달라지지만, 지역 간 상대 순위는 유지되도록 설계했다. 단, 투자안의 신설/증설 구성은 단가 비율에 민감하다.
- 후보지는 시군구 중심점이다. 부지 확보, 임대료, 협력사 계약, 증설 인허가 제약은 반영하지 않는다.
- 수요를 정적으로 본다. 전기차 전환에 따른 차령별 수요 이동을 동적으로 예측하려면 시계열 확장이 필요하다.
- sample 모드의 VOC · 재입고율은 부하 대리변수와 운영 역량 잡음으로 만든 합성값이다. 원인 분리 로직을 검증하는 용도이며, 실제 거점 평가는 live 데이터로 해야 한다.
