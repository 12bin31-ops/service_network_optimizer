# 정비 서비스망 커버리지 갭 분석기

**차령 구조로 지역별 정비 수요를 추정하고, 30분 상권 커버리지의 빈틈을 계량화한 뒤, 신규 거점을 어디에 놓아야 하는지를 최적화로 답한다.**

```bash
pip install -e ".[dev]"
snx pipeline --source sample     # 수집 → 수요 → 커버리지 → 최적화 → 리포트 → 지도
streamlit run app/dashboard.py   # 대시보드
```

API 키 없이 바로 완주한다. 공개 참조표 위에서 재현 가능한 합성 모수를 생성하는 `sample` 모드가 기본값이고, 실제 통계 파일을 `data/raw/` 에 넣으면 `--source live` 로 같은 파이프라인이 그대로 돈다.

---

## 왜 이 문제인가

완성차 국내사업의 서비스 네트워크는 대개 **과거의 판매 실적**을 따라 깔려 있다. 그런데 정비 수요를 만드는 것은 판매량도 인구도 아니라 **지금 도로 위에 굴러다니는 차량의 나이**다. 이 둘이 어긋나면서 두 종류의 구조적 빈틈이 생긴다.

| 갭 유형 | 증상 | 처방 |
|---|---|---|
| **접근성 갭** | 30분 내 도달 가능한 거점이 아예 없다 | 신규 거점 신설 |
| **용량 갭** | 거점은 있는데 이미 포화라 대기가 걸린다 | 워크베이 증설 또는 인근 신설 |

둘을 구분하지 않으면 "정비 불만이 많은 지역"에 무조건 거점을 더 짓는 잘못된 처방이 나온다. 이 프로젝트는 두 갭을 따로 계산하고, 각각 다른 처방을 제시한다.

## 무엇을 만들었나

```
등록 통계 · 인구 · 서비스망
        │
        ├─ [1] 수요 추정      차령 버킷별 정비 원단위 × 공식망 유입률
        │                     → 시군구별 연간 정비 입고 수요
        │
        ├─ [2] 커버리지 진단   30분 상권 판정 + Huff 수요 분배 + 거점 부하율
        │                     → 접근성 갭 / 용량 갭 분리
        │
        ├─ [3] 갭 스코어링     미충족 수요 · 접근시간 · 과부하를 가중 합산 (0~100)
        │
        ├─ [4] 입지 최적화     용량제약 최대커버링 (Capacitated MCLP, CBC)
        │                     → 신규 거점 p개소의 최적 조합
        │
        └─ [5] 리포트 생성     CrewAI 3-에이전트 순차 파이프라인
                              → 임원 보고용 한국어 1페이지
```

### 1. 수요는 차령이 만든다

```
D_i = Σ_a  N_ia · r_a · λ_a
```

`N_ia` 지역 i · 차령버킷 a 의 자사 보유대수, `r_a` 연간 정비 입고 원단위, `λ_a` 공식 서비스망 유입률.

차령이 오르면 `r_a` 는 커지지만 `λ_a` 는 더 빠르게 떨어진다(11년 이상 차량은 일반 정비소로 이탈). 이 비선형성 때문에 **"인구는 적은데 수요는 많은 지역"** 과 **"차는 많은데 공식망 수요는 적은 지역"** 이 갈라진다.

### 2. 수요를 한 거점에 몰아주지 않는다

최근접 거점에 100%를 배정하면 거점이 촘촘한 대도시의 부하가 과대평가된다. 소요시간에 반비례하는 Huff 가중치로 나눠 배정하고, 거점별 부하율을 계산한다.

```
w_ij ∝ max(t_ij, 5분)^(-1.4)      Σ_j w_ij = 1  (30분 내 거점이 있을 때)
```

소요시간은 직선거리 × 우회계수 1.3 ÷ 도시등급별 평균속도로 근사한다. 라우팅 API 로 교체할 수 있게 `coverage/distance.py` 한 함수로 격리해 뒀다.

### 3. 갭 순위대로 짓지 않는다

갭 상위 지역은 서로 인접한 경우가 많다. 1·2·3위에 순서대로 지으면 같은 수요를 세 번 덮는 중복 투자가 된다. 거점 하나가 여러 지역을 덮고 거점 용량은 유한하다는 두 제약을 함께 넣어야 포트폴리오로서 최적인 조합이 나온다.

```
변수   x_j ∈ {0,1}     후보지 j 개설 여부
       z_ij ≥ 0        지역 i 의 미충족 수요 중 신규 거점 j 가 흡수하는 양

max    Σ_ij v_ij · z_ij                  v_ij = 1 + α(1 − t_ij/T)  (접근성 개선 가중)
s.t.   Σ_j z_ij ≤ unmet_i        ∀i      지역별 미충족 수요 한도
       Σ_i z_ij ≤ C · x_j        ∀j      신규 거점 연간 처리 용량
       z_ij = 0  if  t_ij > T            30분 접근 기준 밖은 흡수 불가
       Σ_j x_j ≤ p                       예산 = 신규 거점 개수
```

`x` 만 정수이고 `z` 는 연속이라 규모가 작다(후보 60 · 지역 83 기준 즉시 해). 실행하면 **갭 1~2위인데 신설 대상에서 빠지는 지역**이 나오는데, 이게 이 모형의 핵심 산출물이다 — 미충족 수요가 거점 설계용량의 절반도 안 되면 신설은 용량 과잉이고, 증설이나 협력 정비소 제휴가 맞는 처방이다.

### 4. 에이전트는 숫자를 만들지 않는다

CrewAI 3-에이전트(수요 애널리스트 → 서비스망 전략가 → 보고서 작성자)가 순차로 돌며 리포트를 쓴다. 설계 원칙은 하나다: **에이전트에게는 DB 조회 도구만 준다.** 모든 수치는 `agents/tools.py` 가 SQLite 에서 읽어 JSON 으로 돌려주고, 에이전트는 그 위에 해석과 서술만 얹는다. LLM 이 숫자를 지어내는 경로 자체를 막았다.

`OPENAI_API_KEY` 가 없으면 결정론적 템플릿 리포트로 조용히 폴백한다. 저장소는 어떤 환경에서도 완주한다.

## 산출물

`snx pipeline` 실행 시 `outputs/` 에 생성:

| 파일 | 내용 |
|---|---|
| `report.md` | 전국 진단 · 갭 상위 지역 · 신규 거점 우선순위 · 가정과 한계 |
| `gap_map.html` | 갭 스코어(원 크기 = 미충족 수요) · 기존 거점 · 신규 거점 우선순위 레이어 지도 |
| `siting_priority.csv` | 신규 거점 우선순위표 |
| `center_load.csv` | 거점별 배정 수요와 부하율 |

대시보드는 지도 · 갭 순위 · 거점 부하 분포 · 리포트 4개 탭으로 구성되며, 시도/도시등급 필터가 걸린다.

### 실행 예시 (sample 모드, 시드 고정)

```
연간 정비 입고 수요      4,214,724건
미충족 수요               640,247건 (15.2%)
30분 접근 공백 시군구           1곳
건전 부하율(85%) 초과 상권     43곳

신규 거점 15개소 → 미충족 수요 143,550건 흡수 (전체 미충족의 22.4%)
```

## 사용법

```bash
# 단계별 실행
snx init                          # DB 스키마 생성
snx ingest --source sample        # 차량 모수 · 서비스망 수집
snx demand                        # 지역별 정비 수요 추정
snx analyze                       # 커버리지 · 갭 스코어
snx optimize --p 20               # 신규 거점 20개소 최적 배치
snx report --no-agent             # 템플릿 리포트 (에이전트 없이)
snx map                           # 지도 HTML

# 전 단계 일괄
snx pipeline --source sample --p 15

# 투자 규모별 민감도
for p in 5 10 20 30; do snx optimize --p $p; done
```

설정은 전부 `config/settings.yaml` 에 있다. 정비 원단위, 공식망 유입률, 접근 기준 시간, 평균 주행속도, 갭 스코어 가중치, 거점 규모를 코드 수정 없이 바꿔 시나리오를 돌릴 수 있다.

### live 모드로 전환

`data/raw/` 에 두 파일을 놓으면 된다. 형식과 출처는 `src/snx/ingest/live_sources.py` 상단 주석에 명시해 뒀다.

| 파일 | 내용 | 출처 |
|---|---|---|
| `vehicle_registration.csv` | 시군구 × 차령 × 연료별 등록대수 | 국토교통 통계누리 · KOSIS |
| `service_centers.csv` | 거점 목록(좌표 · 워크베이) | 공식 서비스망 안내 · 사내 네트워크 마스터 |

원본을 코드에서 크롤링하지 않는다. 통계표 배포 형식이 자주 바뀌고 소스별 이용약관이 다르므로, 정규화 책임만 코드가 진다.

## 구조

```
src/snx/
├── config.py            settings.yaml → pydantic 검증 (전역 상수 없음)
├── cli.py               typer CLI — 단계별 / 일괄 실행
├── ingest/              sample 합성 생성기 · live 원본 로더 (동일 인터페이스)
├── storage/             SQLite 어댑터 + schema.sql (단계 산출물 물질화)
├── demand/              차령 기반 수요 추정 + 수요 구성 분해
├── coverage/            거리·소요시간 / 용량 / 커버리지·갭 스코어링
├── optimize/            용량제약 최대커버링 (PuLP · CBC)
├── agents/              CrewAI 크루 + 조회 도구 + prompts/*.yaml
├── report/              근거표 조립 · 마크다운 렌더링
└── viz/                 folium 지도
app/dashboard.py         Streamlit 대시보드
tests/                   37 tests — 수요 모형 폐형해 검증, 커버리지 경계조건,
                         최적화 단조성·예산제약, 엔드투엔드 통합
```

단계 산출물을 메모리가 아니라 SQLite 에 물질화한다. 각 단계를 독립적으로 재실행할 수 있고, 대시보드와 에이전트가 동일한 단일 소스를 읽는다.

## 한계

- 소요시간은 직선거리 기반 근사치다. 산악 지형과 도서 지역의 접근성이 실제보다 낙관적으로 나온다.
- 정비 원단위와 공식망 유입률은 시나리오 가정값이다. 실적 데이터로 교체하면 절대 수준은 바뀌지만 지역 간 상대 순위는 유지되는 구조로 설계했다.
- 후보지는 시군구 중심점이다. 부지 확보, 임대료, 대리점 계약 제약은 반영하지 않는다 — "어느 시군구에 필요한가" 까지가 산출 범위다.
- 정비 수요를 정적으로 본다. 전기차 전환에 따른 차령별 수요 이동을 동적으로 예측하려면 시계열 확장이 필요하다.
